## 1. 중복코드 허용하기

> **<font color="#c0504d">요약!</font>**<br>
> 중복코드가 너무 많은거 아니면 추상화 공통화부터 하지말고 그냥  중복코드 허용하자.

- 무작정 추상화나 공통화를 하지말고, 충분히 고려한 후 추상화나 공통화를 하자. 

### 중복 코드 예시

```js
function func1() {
	return (
		<div>
			<h2>
				Hello world!
			</h2>
		</div>
	)
}
```

해당 컴포넌트가 3~4곳에서 사용되어 컴포넌트로 분리했다고 가정해보자.

근데 만약 <br>
A라는 곳에서는 button태그가 필요하고<br>
B라는 곳에서는 input태그가 필요하고<br>
C라는 곳에서는 table태그가 필요하다고 해보자.

그럴때마다 props를 받아서 분기를 나눠서 반환해야할까?

무작정 추상화나 공통화를 하기전에

해당 컴포넌트나 함수, Hook이 변화될 여지가 있는지, 정확하게 동일하게만 유지되어 사용되는지, 

충분히 고려를 한 후, 동작이 달라질 여지가 있으면 중복코드를 허용하는것이 더 좋은 선택이다.

공통화를 할 부분을 공통화 하고, 나머지는 중복으로 유지하는 방법도 존재할 수 있다.

## 2. props drilling 지우기

> **<font color="#c0504d">요약!</font>**<br>
> props drilling이 생겼다? 부모와 자식컴포넌트 사이에 강한 결합이 생긴거임 ㅅㄱ.

- props drilling은 정말로 피해보자.

props drilling은 예시로 보여주기가 힘드니 사진으로 코드를 대체하겠다.

### props drilling 예시

![](public/asset/posts/props%20drilling.png)

이런 경우가 생긴다.

만약 루트 노드 컴포넌트부터 depth가 가장 깊은 단말 노드 컴포넌트까지 props를 일반적으로 전달하려면,<br>
중간에 있는 모든 단말노드 컴포넌트의 부모 컴포넌트들은 단순히 props전달만을 위해 상위 노드들과 묶이게 된다.

즉, 강한 결합이 props drilling으로 인해 생기게 되는것이다.

이런 문제를 해결하기 위해선 몇가지 방법이 존재한다.

#### 해결법 A. 조합 컴포넌트 사용

> 조합 컴포넌트 패턴은 props drilling 문제를 완전히 해결하는것은 아니고, 줄이는데 도움을 준다.

```jsx
function ItemEditModal({ open, items, recommendedItems, onConfirm, onClose }) {
  const [keyword, setKeyword] = useState("");

  return (
    <Modal open={open} onClose={onClose}>
      <ItemEditList onClose={onClose}>
        <ItemEdit
          keyword={keyword}
          items={items}
          recommendedItems={recommendedItems}
          onConfirm={onConfirm}
        />
      </ItemEditList>
    </Modal>
  );
}

function ItemEditList({ children, onClose }) {
  return (
    <>
      <div style="display: flex; justify-content: space-between;">
        <Input
          value={keyword}
          onChange={(e) => onKeywordChange(e.target.value)}
        />
        <Button onClick={onClose}>닫기</Button>
      </div>
      {children}
    </>
  );
}
```

어떻게 props drilling을 해결하는걸까?

기본적으로 리액트의 컴포넌트 구조는 다음과 같다.

`Main` -> `FirstPage` -> `FirstList` -> `First`

그래서 first에 필요한 것이 secondPage에서도 필요하다면<br>
Main에서 필요한것을 선언한후에 <br>
`FirstPage` -> `FirstList` -> `First`로 props를 내려줘야한다.

하지만 합성 컴포넌트 패턴을 쓰면 약간 해소가 되는데, 
> `ItemEditList`컴포넌트에서 리액트 전용 예약어 children을 이용해서, `Main`에서 `ItemEditList`내려온 props를 `ItemEdit`으로 직접 넘겨주지 않아도, <br> 직접 사용하도록 할 수 있다.

하지만 근본적인 props drilling 해결법은 아니다! 

합성컴포넌트는 `재사용성`과 `유연성`을 높이기 위해 사용한다.
- 컴포넌트의 틀을 만들고, 그 안에서 원하는 내용을 동적으로 삽입할 수 있게 함
- `react-router-dom`의 `Outlet`컴포넌트가 아주 좋은 합성 컴포넌트의 예시이다.
	- [[React] react-router-dom의 Outlet컴포넌트](http://localhost:5173/[React]%20react-router-dom%EC%9D%98%20Outlet%EC%BB%B4%ED%8F%AC%EB%84%8C%ED%8A%B8)

#### 해결법 B. React context api사용

`createContext` 와 `useContext`에 해당되는 부분이다.

`createContext`로 해당 상태나 변수를 providing해주면 된다.

> <font color="#c0504d">주의사항</font>
>
> 모든 props drilling을 contextAPI로 해결해야 하는건 아니다.
> - 컴포넌트의 역할과 의도를 담고있는 props라면 문제가 없다.
> - children prop을 이용해 depth를 줄일수 있다면 그걸 선호하자.
> 	- 데이터를 사용하지 않는 단순히 값을 전달하기 위한 용도의 컴포넌트는 props가 컴포넌트의 역할과 의도를 나타내지 않을 수 있다. 
> 	- 이러한 경우에 조합(Composition) 패턴을 사용한다면 불필요한 depth를 줄일 수 있다.
>
> 위의 내용을 고려해보고 접근방법이 맞지않으면 그때 contextAPI를 이용해보도록 하자.

중요한 사실이 남았다

`contextAPI`는 리렌더링의 문제가 있다.

간단한 경우 useMemo와 같은 최적화 훅을 이용해 문제를 해결할 수 있지만, 
너무 다양한곳에서 사용되어야하는경우, 

`zustand`나 `redux`와 같은 상태관리라이브러리를 사용해보는걸 추천한다.
