## 1. 함께 수정되는 파일을 물리적으로 곁에 두기

> **<font color="#c0504d">요약!</font>**<br>
> DomainA에 필요한 컴포넌트, 유틸, 훅은 같은 디렉토리로! DomainB~DomainZ까지 전체적으로 필요하다면 global!

- 단순히 util, consts, component만 분리하는것이 아닌, 모듈에 따라서 나눠야 한다. 

```txt
└─ src
   ├─ components
   ├─ constants
   ├─ containers
   ├─ contexts
   ├─ remotes
   ├─ hooks
   ├─ utils
   └─ ...
```

문제점
1. 파일을 이렇게 종류별로 나누게 되면 어떤 코드가 어떤 코드를 참조하는지 파악에 용이하지 않다.
	1. 모두 개발자의 몫!
2. 특정 컴포넌트나 훅, util등이 삭제되어야 할때, 연관된 코드가 함께 삭제되지 못해서 코드가 남아있게 될 수도 있다.
3. 프로젝트가 커짐에 따라, 디렉토리가 비대해질 가능성이 커지고, 의존관계가 복잡해 진다.

해결법은 함께 있어야 할 파일들을 물리적으로 가까운곳에 위치시키면 된다.

```txt
└─ src
   │  // 전체 프로젝트에서 사용되는 코드
   ├─ components
   ├─ containers
   ├─ hooks
   ├─ utils
   ├─ ...
   │
   └─ Domains
      │
      └─ Domain1&2
         │   // Domain 1, 2에서 공통으로 사용되는 코드
         ├─  components
		 ├─  hooks
		 │
         │  // Domain1에서만 사용되는 코드
	     ├─ Domain1
         │     ├─ components
         │     ├─ containers
	     │     ├─ hooks
	     │     ├─ utils
	     │     └─ ...
	     │
	     │  // Domain2에서만 사용되는 코드
	     └─ Domain2
	           ├─ components
	           ├─ containers
	           ├─ hooks
	           ├─ utils
	           └─ ...
```

## 2. 폼의 응집도 생각하기

> **<font color="#c0504d">요약!</font>**<br>
> DomainA에 필요한 컴포넌트, 유틸, 훅은 같은 디렉토리로! DomainB~DomainZ까지 전체적으로 필요하다면 global!

- 단순히 util, consts, component만 분리하는것이 아닌, 모듈에 따라서 나눠야 한다. 

폼을 사용할때, 검증과 더불어 다양한 것을 신경써야 한다.

이렇게 폼관리에 있어 어느 방식을 선호하면 좋을지 알아보자.

### 폼 검증 및 제출 예시

#### 필드단위 응집도

```jsx
import { useForm } from "react-hook-form";

export function Form() {
  const {
    register,
    formState: { errors },
    handleSubmit
  } = useForm({
    defaultValues: {
      name: "",
      email: ""
    }
  });

  const onSubmit = handleSubmit((formData) => {
    // 폼 데이터 제출 로직
    console.log("Form submitted:", formData);
  });

  return (
    <form onSubmit={onSubmit}>
      <div>
        <input
          {...register("name", {
            validate: (value) =>
              isEmptyStringOrNil(value) ? "이름을 입력해주세요." : ""
          })}
          placeholder="이름"
        />
        {errors.name && <p>{errors.name.message}</p>}
      </div>

      <div>
        <input
          {...register("email", {
            validate: (value) => {
              if (isEmptyStringOrNil(value)) {
                return "이메일을 입력해주세요.";
              }

              if (!/^[A-Z0-9._%+-]+@[A-Z0-9.-]+\.[A-Z]{2,}$/i.test(value)) {
                return "유효한 이메일 주소를 입력해주세요.";
              }

              return "";
            }
          })}
          placeholder="이메일"
        />
        {errors.email && <p>{errors.email.message}</p>}
      </div>

      <button type="submit">제출</button>
    </form>
  );
}

function isNil(value: unknown): value is null | undefined {
  return value == null;
}

type NullableString = string | null | undefined;

function isEmptyStringOrNil(value: NullableString): boolean {
  return isNil(value) || value.trim() === "";
}
```

작동원리는 다음과 같다.
1. Form컴포넌트를 만든다.
2. react-hook-form라이브러리의 useForm훅을 이용해 폼 데이터를 관리
	1. `register`, `formState{errors}`, `handleSubmit`
	2. defaultValue를 이용해 name필드와 email필드의 기본 입력값을 빈문자열로 설정
3. onSubmit으로 폼 제출시에 실행될 로직 정의
4. `isNil`메서드로, value는  `unknown`타입이지만, 함수가 true를 반환하면 `null|undefined`로 간주됨.
	1. `is`문법 => [TS 타입가드](https://seokzin.tistory.com/entry/TypeScript-%ED%83%80%EC%9E%85-%EA%B0%80%EB%93%9C-Type-Guard)
5. `isEmptyStringOrNil`메서드로, value를 `isNil`을 이용해 `isNil(value)`, `value.trim() === ""`중 하나라도 참이면 참을 반환
	1. value가 null, undefined, 빈 문자열 일경우 true 반환
6. 이름 입력필드
	1. `register("name", {...})` → 이름 입력 필드를 `react-hook-form`에 등록
	2. validate로 검증로직 (`isEmptyStringOrNil`)을 사용해 null/undefined/빈 문자열이면 에러발생
	3. 에러가 발생하면 에러 메세지 출력
7. 이메일 입력필드
	1. . `register("email", {...})` → 이름 입력 필드를 `react-hook-form`에 등록
	2. validate로 검증로직 (`isEmptyStringOrNil`)을 사용해 null/undefined/빈 문자열이거나, 정규표현식에 맞지 않는 이메일 형식이면, 에러
	3. 에러가 발생하면 에러 메세지 출력

즉, 각 필드가 각 고유의 검증로직을 가져서,  변경이 필요한 부분이 적어 유지보수가 쉬워지는 방식이다.


#### 폼 전체 단위 응집도

```jsx
import * as z from "zod";
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";

const schema = z.object({
  name: z.string().min(1, "이름을 입력해주세요."),
  email: z
    .string()
    .min(1, "이메일을 입력해주세요.")
    .email("유효한 이메일 주소를 입력해주세요.")
});

export function Form() {
  const {
    register,
    formState: { errors },
    handleSubmit
  } = useForm({
    defaultValues: {
      name: "",
      email: ""
    },
    resolver: zodResolver(schema)
  });

  const onSubmit = handleSubmit((formData) => {
    // 폼 데이터 제출 로직
    console.log("Form submitted:", formData);
  });

  return (
    <form onSubmit={onSubmit}>
      <div>
        <input {...register("name")} placeholder="이름" />
        {errors.name && <p>{errors.name.message}</p>}
      </div>

      <div>
        <input {...register("email")} placeholder="이메일" />
        {errors.email && <p>{errors.email.message}</p>}
      </div>

      <button type="submit">제출</button>
    </form>
  );
}
```

작동원리는 비슷하다.

다만 하나의 차이가 있다면<br>
검증로직이 폼에 종속되어, 변경단위가 폼 단위로 발생할때 고려하면 좋은 방식이다.

### 필드단위 VS 폼 전체 단위 (응집도)

|비교 항목|필드 단위 응집도|폼 전체 단위 응집도|
|---|---|---|
|**검증 방식**|개별 필드별로 검증 로직을 적용|폼 전체에 대한 일괄적인 검증 적용|
|**검증 위치**|각 필드에서 직접 정의 (`register` 옵션 내에서 처리)|별도의 스키마(`schema` 또는 `resolver`)에서 처리|
|**유지보수성**|개별 필드 수정이 쉬움, 특정 필드만 변경 가능|폼 단위로 관리되므로 전체적인 일관성을 유지하기 쉬움|
|**재사용성**|필드 단위로 재사용 가능 (`useForm`과 별개로 개별 컴포넌트로 추출 가능)|폼 단위로 사용되므로 특정 폼에서만 유용|
|**필드 간 의존성**|각 필드가 독립적으로 동작|여러 필드가 서로 의존하는 로직을 쉽게 정의 가능|
|**적합한 경우**|필드가 독립적이고 여러 폼에서 재사용 가능할 때|필드들이 밀접하게 연결되고 일괄적인 검증이 필요할 때|

어느 상황에 어떤걸 선호하면 좋을까?

- 필드 단위
	- **독립적인 검증이 필요할 때**
		- 필드별로 복잡한 검증로직이나 비동기 검증이 필요한 경우
		- 이메일 형식, 전화번호 유효성, 아이디 중복, 추천코드 유효성 처럼 각 필드가 독립적이로 고유한 검증이 필요한 경우
	- **재사용이 필요할 떄**
		- 필드 혹은 검증록직이 다른 폼에서도 사용될 수 있는 경우
- 폼 전체 단위
	- **단일 기능**
		- 모든 필드가 밀접하게 관련돼, 하나의 완결된 기능을 구성하는 경우
		- 결제 정보나 배송 정보처럼 모든 필드가 하나의 비즈니스 로직을 이룰때
	- **단계별 입력이 필요할 때**
		- 회원가입이나 설문조사처럼 이전 단계의 입력값이 다음단계에 영향을 주는 경우
		- \~~마법사 처럼 마법사 form처럼 스텝별로 동작할때
	- **필드간 의존성이 있을때**
		- 여러 필드가 서로를 참조하거나 영향을 주는 경우
		- 비밀번호 확인이나 총액 계산과 같은 필드간 상호작용이 필요한 경우

### 어떤 기준으로 뭘 선택하면 될까?

- **폼이 크고 복잡한가?** → **폼 전체 단위 응집도** 사용
- **필드별로 분리해서 사용할 가능성이 있는가?** → **필드 단위 응집도** 사용
- **필드 간의 상호작용이 있는가?** → **폼 전체 단위 응집도** 사용
- **검증 로직이 자주 변경될 가능성이 있는가?** → **필드 단위 응집도** 사용
