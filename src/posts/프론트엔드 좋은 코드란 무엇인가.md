가장 중요한 개념은 4가지 이다.

- 가독성
	- 코드가 얼마나 읽기 쉬운지, 그 정도를 의미한다.
	- 코드 변경이 쉬우려면 코드가 어떤 동작을 하는지 이해할 수 있어야 한다.
	- **읽기 좋은 코드**는 사람이 머릿속에서 고려하는 맥락이 적고, 위에서 아래로 자연스럽게 이어진다.
- 예측 가능성
	- 협업시에 함수나 컴포넌트의 동작이 얼마나 예측가능한지 의미한다.
	- **예측 가능성이 높은 코드**는 일관된 컨벤션을 따라서, 함수나 컴포넌트의 이름과 파라미터, 반환값만 보고도 어떤 동작을 하는지 알수있다.
- 응집도
	- 수정되어야 할 코드가 항상 같이 수정되는지를 의미한다.
	- **응집도가 높은 코드**는 수정시에 구조적으로 항상 수정되어야할 부분이 수정된다.
- 결합도
	- 결합도는 코드를 수정했을때의 영향범위를 의미한다.
	- 코드를 수정시에 영향범위가 적어서 예측할 수 있는 코드가 수정하기 쉬운코드다.
	- 즉, **결합도가 낮을수록** 좋은 코드이다

아래의 4가지 모두를 만족하는 코드를 짜기는 어렵다.
>추상화를 거치면 거칠수록 **응집도**는 높아지지만 **가독성**은 낮아지고,
>
> 중복코드를 허용하면 코드의 영향범위를 낮출수 있어 **결합도**를 낮출수 있지만, 
> 
> 중복된 코드의 수정이 필요할때 한쪽만 수정하면, 다른쪽을 실수로 수정못할수도 있기에 **응집도**가 낮아진다.

## 가독성
### 1. 같이 실행되지 않는 코드 분리하기

> **<font color="#c0504d">요약!</font>**<br>
> 맥락, 분기에 따라 코드를 나눠서 가독성을 올리자.

- 동시에 실행되지 않는 코드가 하나의 컴포넌트에 같이 들어가 있으면 가독성이 떨어진다.

#### 확인버튼 예시

```jsx
function SubmitButton() {
  const isViewer = useRole() === "viewer";

  useEffect(() => {
    if (isViewer) {
      return;
    }
    showButtonAnimation();
  }, [isViewer]);

  return isViewer ? (
    <TextButton disabled>Submit</TextButton>
  ) : (
    <Button type="submit">Submit</Button>
  );
}
```

이런 확인을 누르는 버튼이 존재한다고 해보자.
</br></br>
isViewer라는 분기를 이용해서 
</br>
true라면 `TextButton`컴포넌트가 disabled되고, </br>
false라면 `Button`컴포넌트가 클릭되도록 코드가 짜져있다.

</br>
또 `useEffect`로 isViewer라는 의존배열을 통해 
isViewer의 변화가 일어날때마다 </br>
true이면, 아무일도 일어나지 않고</br>
false이면, `showButtonAnimation()`이라는 메서드가 실행되게 된다
</br></br>
즉 코드를 살펴보면
2가지의 분기로 코드가 구성되어 있는걸 확인할 수 있다.

isViewer를 기준으로,
1. isViewer가 true인 경우, 즉, viewer인 경우
2. isViewer가 false인 경우, 즉, viewer가 아닌 경우
</br></br>

그러므로 코드를 다음과 같은 형태로 변경할 수 있다.

```jsx
//isViewer분기
function SubmitButton() {
  const isViewer = useRole() === "viewer";

  return isViewer ? <ViewerSubmitButton /> : <AdminSubmitButton />;
}

//isViewer === true일때
function ViewerSubmitButton() {
  return <TextButton disabled>Submit</TextButton>;
}

//isViewer === false일때
function AdminSubmitButton() {
  useEffect(() => {
    showAnimation();
  }, []);

  return <Button type="submit">Submit</Button>;
}
```

다만 단점도 존재를 한다.
- 만약, 두 분기에 따른 컴포넌트가 공통된 부분(e.g CSS)이 필요해질때, 수정될수록 두 컴포넌트를 우리가 기억하고
   수정을 하기란 어렵다.
	- 이것을 해결하기위해 공통된 모듈을 사용한다면, 컴포넌트를 나눈 의미가 퇴행된다.

이런경우엔</br>
공통적인 스타일이 적용된 baseButton컴포넌트를 만들어, 각 컴포넌트에서 의미에 맞게 사용되도록 하면 됨.

```jsx
function SubmitButton() {
  const isViewer = useRole() === "viewer";

  return isViewer ? <ViewerSubmitButton /> : <AdminSubmitButton />;
}

function ViewerSubmitButton() {
  return <ButtonBase disabled>Submit</ButtonBase>;
}

function AdminSubmitButton() {
  useEffect(() => {
    showAnimation();
  }, []);

  return <ButtonBase type="submit">Submit</ButtonBase>;
}

function ButtonBase() {
  return (<Button css={{
    background: ...,
    border: ...,
    shadow: ...,
>Submit</Button>)
}
```


### 2. 구현 상세 추상화하기

> **<font color="#c0504d">요약!</font>**<br>
> 맥락에 따라 구현부를 추상화 하자.

- 코드를 읽을때 개발자 한명이  동시에 고려할 수 있는 맥락의 갯수는 한정되어 있다.

아래의 코드를 살펴보자.
#### 로그인 예시
```jsx
function LoginStartPage() {
  useCheckLogin({
    onChecked: (status) => {
      if (status === "LOGGED_IN") {
        location.href = "/home";
      }
    }
  });

  /* ... 로그인 관련 로직 ... */

  return <>{/* ... 로그인 관련 컴포넌트 ... */}</>;
}
```

해당 컴포넌트는 로그인된 상태인지 확인하여<br>
`useCheckLogin()`이라는 커스텀 훅을 이용해 onCheck콜백으로 현재 status를 받아서 로그인 된 상태라면 `location.href`를 이용해 `/home` 으로 이동되도록 한다.
<br><br>
문제는 다음과 같다.

Login페이지 컴포넌트인데, 로그인을 체크해서 리다이렉트 시키는 코드가 공존.
즉, 2개의 다른 개념의 맥락이 존재한다.
<br><br>
또, `useCheckLogin()` 훅에서 사용되는 많은 종류의 변수로 인해 해당 커스텀 훅 전체를 살펴봐야 무슨 의미의 코드인지 알 수 있게된다.

<br><br>
이럴땐, 두 맥락을 나누어서 코드를 짜면 된다.

HOC(Higher-Order component) 혹은 Wrapper컴포넌트를 사용하면 된다.

##### Option A. wrapper 컴포넌트 사용하기

```jsx
function App() {
  return (
    <AuthGuard>
      <LoginStartPage />
    </AuthGuard>
  );
}

function AuthGuard({ children }) {
  const status = useCheckLoginStatus();

  useEffect(() => {
    if (status === "LOGGED_IN") {
      location.href = "/home";
    }
  }, [status]);

  return status !== "LOGGED_IN" ? children : null;
}

function LoginStartPage() {
  /* ... 로그인 관련 로직 ... */

  return <>{/* ... 로그인 관련 컴포넌트 ... */}</>;
}
```
이렇게 AuthGuard라는 컴포넌트에 사용자의 로그인 상태를 관리하고, 
react의 children props를 이용해 로그인 상태에 맞춰서 원하는 컴포넌트를 렌더링 해주도록 하면 된다.
<br><br>
AuthGuard내에서도 status를 명시적으로 작성해주어, 
`useEffect`내부에서도 한가지의 변수로 코도를 작성하여 가독성을 올림.

##### Option B. HOC 사용하기

```jsx
function LoginStartPage() {
  /* ... 로그인 관련 로직 ... */

  return <>{/* ... 로그인 관련 컴포넌트 ... */}</>;
}

export default withAuthGuard(LoginStartPage);

// HOC 정의
function withAuthGuard(WrappedComponent) {
  return function AuthGuard(props) {
    const status = useCheckLoginStatus();

    useEffect(() => {
      if (status === "LOGGED_IN") {
        location.href = "/home";
      }
    }, [status]);

    return status !== "LOGGED_IN" ? <WrappedComponent {...props} /> : null;
  };
}
```

신기한 패턴이다.

1. `withAuthGuard`라는 고차 컴포넌트를 호출한다. <- 기존 컴포넌트를 감싸는 역할
	1. AuthGuard라는 컴포넌트를 리턴한다.
	2. status를 명시적으로 작성하여 `useEffect`를 사용함에 있어 가독성을 올림
	3. status에 따라서 로그인이 된 사용자가 아니라면, `withAuthGuard`의 props로 받은 WrappedComponent를 `AuthGuard`의 props인 props를 이용해 렌더링 한다.
2. `LoginStartPage`는 `withAuthGuard()`고차 컴포넌트로 감싸져서 export된다.
	1. 리턴되는 `LoginStartPage`컴포넌트는 `withAuthGuard`로 감싸져있다.
	2. 그래서 `LoginStartPage`컴포넌트가 렌더링 되지 않고,<br>`withAuthGuard`의 반환값인 `AuthGuard`컴포넌트가 대신 렌더링 된다.
	3. 즉, `LoginStartPage`컴포넌트의 props는 자동적으로 `AuthGuard`의 props로 전달되게 된다.

이런식으로 작동하게 된다.
