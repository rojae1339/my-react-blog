## 맥락 줄이기
### 1. 같이 실행되지 않는 코드 분리하기

> **<font color="#c0504d">요약!</font>**<br>
> 맥락, 분기에 따라 코드를 나눠서 가독성을 올리자.

- 동시에 실행되지 않는 코드가 하나의 컴포넌트에 같이 들어가 있으면 가독성이 떨어진다. 

#### 확인버튼 예시

```jsx
function SubmitButton() {
  const isViewer = useRole() === "viewer";

  useEffect(() => {
    if (isViewer) {
      return;
    }
    showButtonAnimation();
  }, [isViewer]);

  return isViewer ? (
    <TextButton disabled>Submit</TextButton>
  ) : (
    <Button type="submit">Submit</Button>
  );
}
```

간단하게 무슨코드인지 살펴보자.
1. isViewer라는 분기를 이용해서 
	1. true라면 `TextButton`컴포넌트가 disabled되고, </br>
	2. false라면 `Button`컴포넌트가 클릭되도록 코드가 짜져있다.
2. `useEffect`로 isViewer라는 의존배열을 통해 isViewer의 변화가 일어날때마다 
	1. true이면, 아무일도 일어나지 않고
	2. false이면, `showButtonAnimation()`이라는 메서드가 실행되게 된다
</br></br>
즉 코드를 살펴보면
2가지의 분기로 코드가 구성되어 있는걸 확인할 수 있다.

isViewer를 기준으로,
1. isViewer가 true인 경우, 즉, viewer인 경우
2. isViewer가 false인 경우, 즉, viewer가 아닌 경우
</br></br>

그러므로 코드를 다음과 같은 형태로 변경할 수 있다.

```jsx
//isViewer분기
function SubmitButton() {
  const isViewer = useRole() === "viewer";

  return isViewer ? <ViewerSubmitButton /> : <AdminSubmitButton />;
}

//isViewer === true일때
function ViewerSubmitButton() {
  return <TextButton disabled>Submit</TextButton>;
}

//isViewer === false일때
function AdminSubmitButton() {
  useEffect(() => {
    showAnimation();
  }, []);

  return <Button type="submit">Submit</Button>;
}
```

다만 단점도 존재를 한다.
- 만약, 두 분기에 따른 컴포넌트가 공통된 부분(e.g CSS)이 필요해질때, 수정될수록 두 컴포넌트를 우리가 기억하고
   수정을 하기란 어렵다.
	- 이것을 해결하기위해 공통된 모듈을 사용한다면, 컴포넌트를 나눈 의미가 퇴행된다.

이런경우엔</br>
공통적인 스타일이 적용된 baseButton컴포넌트를 만들어, 각 컴포넌트에서 의미에 맞게 사용되도록 하면 됨.

```jsx
function SubmitButton() {
  const isViewer = useRole() === "viewer";

  return isViewer ? <ViewerSubmitButton /> : <AdminSubmitButton />;
}

function ViewerSubmitButton() {
  return <ButtonBase disabled>Submit</ButtonBase>;
}

function AdminSubmitButton() {
  useEffect(() => {
    showAnimation();
  }, []);

  return <ButtonBase type="submit">Submit</ButtonBase>;
}

function ButtonBase() {
  return (<Button css={{
    background: ...,
    border: ...,
    shadow: ...,
>Submit</Button>)
}
```


### 2. 구현 상세 추상화하기

> **<font color="#c0504d">요약!</font>**<br>
> 한번에 고려해야할 맥락의 갯수를 추상화를 통해 요약하자!

- 코드를 읽을때 개발자 한명이  동시에 고려할 수 있는 맥락의 갯수는 한정되어 있다.

아래의 코드를 살펴보자.
#### 로그인 예시
```jsx
function LoginStartPage() {
  useCheckLogin({
    onChecked: (status) => {
      if (status === "LOGGED_IN") {
        location.href = "/home";
      }
    }
  });

  /* ... 로그인 관련 로직 ... */

  return <>{/* ... 로그인 관련 컴포넌트 ... */}</>;
}
```

간단하게 코드를 살펴보자.

1. 해당 컴포넌트는 로그인된 상태인지 확인하여<br>
`useCheckLogin()`이라는 커스텀 훅을 이용해 <br> onCheck콜백으로 현재 status를 받아서 로그인 된 상태라면 `location.href`를 이용해 `/home` 으로 이동되도록 한다.
<br><br>

뭐가 문제일까?

Login페이지 컴포넌트인데, 로그인을 체크해서 리다이렉트 시키는 코드가 공존.
즉, 2개의 다른 개념의 맥락이 존재한다.
<br><br>
또, `useCheckLogin()` 훅에서 사용되는 많은 종류의 변수로 인해 해당 커스텀 훅 전체를 살펴봐야 무슨 의미의 코드인지 알 수 있게된다.

<br><br>
이럴땐, 두 맥락을 나누어서 코드를 짜면 된다.

HOC(Higher-Order component) 혹은 Wrapper컴포넌트를 사용하면 된다.

##### 해결법 A. wrapper 컴포넌트 사용하기

```jsx
function App() {
  return (
    <AuthGuard>
      <LoginStartPage />
    </AuthGuard>
  );
}

function AuthGuard({ children }) {
  const status = useCheckLoginStatus();

  useEffect(() => {
    if (status === "LOGGED_IN") {
      location.href = "/home";
    }
  }, [status]);

  return status !== "LOGGED_IN" ? children : null;
}

function LoginStartPage() {
  /* ... 로그인 관련 로직 ... */

  return <>{/* ... 로그인 관련 컴포넌트 ... */}</>;
}
```
이렇게 AuthGuard라는 컴포넌트에 사용자의 로그인 상태를 관리하고, 
react의 children props를 이용해 로그인 상태에 맞춰서 원하는 컴포넌트를 렌더링 해주도록 하면 된다.
<br><br>
AuthGuard내에서도 status를 명시적으로 작성해주어, 
`useEffect`내부에서도 한가지의 변수로 코드를 작성하여 가독성을 올림.

##### 해결법 B. HOC 사용하기

```jsx
function LoginStartPage() {
  /* ... 로그인 관련 로직 ... */

  return <>{/* ... 로그인 관련 컴포넌트 ... */}</>;
}

export default withAuthGuard(LoginStartPage);

// HOC 정의
function withAuthGuard(WrappedComponent) {
  return function AuthGuard(props) {
    const status = useCheckLoginStatus();

    useEffect(() => {
      if (status === "LOGGED_IN") {
        location.href = "/home";
      }
    }, [status]);

    return status !== "LOGGED_IN" ? <WrappedComponent {...props} /> : null;
  };
}
```

신기한 패턴이다.

1. `withAuthGuard`라는 고차 컴포넌트를 호출한다. <- 기존 컴포넌트를 감싸는 역할
	1. AuthGuard라는 컴포넌트를 리턴한다.
	2. status를 명시적으로 작성하여 `useEffect`를 사용함에 있어 가독성을 올림
	3. status에 따라서 로그인이 된 사용자가 아니라면, `withAuthGuard`의 props로 받은 WrappedComponent를 `AuthGuard`의 props인 props를 이용해 렌더링 한다.
2. `LoginStartPage`는 `withAuthGuard()`고차 컴포넌트로 감싸져서 export된다.
	4. 리턴되는 `LoginStartPage`컴포넌트는 `withAuthGuard`로 감싸져있다.
	5. 그래서 `LoginStartPage`컴포넌트가 렌더링 되지 않고,<br>`withAuthGuard`의 반환값인 `AuthGuard`컴포넌트가 대신 렌더링 된다.
	6. 즉, `LoginStartPage`컴포넌트의 props는 자동적으로 `AuthGuard`의 props로 전달되게 된다.

이런식으로 작동하게 된다.

### 3. 로직 종류에 따라 합쳐진 함수 쪼개기

> **<font color="#c0504d">요약!</font>**<br>
> 단일 책임 원칙을 생각하자!

- 쿼리 파라미터, 상태, API 호출과 같은 로직의 종류에 따라 함수/컴포넌트/Hook을 만들지 말아라.

코드를 살펴보자

#### 전체 파라미터 관리 커스텀 훅 예시
```jsx
import moment, { Moment } from "moment";
import { useMemo } from "react";
import {
  ArrayParam,
  DateParam,
  NumberParam,
  useQueryParams
} from "use-query-params";

const defaultDateFrom = moment().subtract(3, "month");
const defaultDateTo = moment();

export function usePageState() {
  const [query, setQuery] = useQueryParams({
    cardId: NumberParam,
    statementId: NumberParam,
    dateFrom: DateParam,
    dateTo: DateParam,
    statusList: ArrayParam
  });

  return useMemo(
    () => ({
      values: {
        cardId: query.cardId ?? undefined,
        statementId: query.statementId ?? undefined,
        dateFrom:
          query.dateFrom == null ? defaultDateFrom : moment(query.dateFrom),
        dateTo: query.dateTo == null ? defaultDateTo : moment(query.dateTo),
        statusList: query.statusList as StatementStatusType[] | undefined
      },
      controls: {
        setCardId: (cardId: number) => setQuery({ cardId }, "replaceIn"),
        setStatementId: (statementId: number) =>
          setQuery({ statementId }, "replaceIn"),
        setDateFrom: (date?: Moment) =>
          setQuery({ dateFrom: date?.toDate() }, "replaceIn"),
        setDateTo: (date?: Moment) =>
          setQuery({ dateTo: date?.toDate() }, "replaceIn"),
        setStatusList: (statusList?: StatementStatusType[]) =>
          setQuery({ statusList }, "replaceIn")
      }
    }),
    [query, setQuery]
  );
}
```

간단하게 무슨 코드인지 살펴보자
1. use query params라이브러리를 이용해 `usePageState()`라는 상태 커스텀 훅을 반환한다.
2. useMemo로 각 파라미터의 변화가 있을때 리렌더링 되고 아닌경우엔 그전의 값을 그대로 반환하도록 최적화를 했다.

<br>
객체지향 원칙을 `SOLID` 원칙이라고 부른다.
<br><br>
여기서 S에 해당되는 원칙이 `Single Responsibility Principle`로, `단일책임 원칙` 이라고 불린다.

뭐가 문제일까?

1. 코드의 양이 점점 방대해지고, 각 코드부분이 무슨 역할을 하게 되는지 확실한 맥락 파악이 힘들어진다.
	1. "새로운 쿼리 파라미터에 대한 요구사항이 생긴다" 라고 가정을 해보면, 
	2. 이 Hook이 전체적으로 파라미터를 관리한다는걸 알고있다.
	3. 무의식적으로 여기서 코드를 추가적으로 작성하게 된다.
2. `useMemo`라는 최적화를 한 의미가 없어진다.
	4. 의존배열로 query, setQuery를 받는다.
	5. 하지만 하나의 useMemo에서 여러가지의 query들을 전체적으로 관리하고 있다.
	6. 예를들어 cardId 라는 1개의 query에 변화가 있다고 하더라도, 전체적으로 리렌더링이 되게 된다.

그럼 어떻게 해결을 해야할까?

```jsx
import { NumberParam, useQueryParam } from "use-query-params";

export function useCardIdQueryParam() {
  const [cardId, _setCardId] = useQueryParam("cardId", NumberParam);

  const setCardId = useCallback((cardId: number) => {
    _setCardId({ cardId }, "replaceIn");
  }, []);

  return [cardId ?? undefined, setCardId] as const;
}
```

> 단일 책임으로 Hook을 분리해주면 된다.

## 이름 붙이기

### 1. 복잡한 조건에 이름 붙이기

> **<font color="#c0504d">요약!</font>**<br>
> 조건을 명시적으로 나타내어 가독성을 올리자!

- 조건식에 특별한 이름이 없이 나열이 되기 시작하면, 한눈에 무엇을 원하는 코드인지 알아차리기 힘들다.

#### 상품 필터링 예시
```jsx
const result = products.filter((product) =>
  product.categories.some(
    (category) =>
      category.id === targetCategory.id &&
      product.prices.some(
        (price) => minPrice <= price && price <= maxPrice
      )
  )
);
```

비교적 간단한 코드다.

단순하게 살펴본 동작원리는 다음과 같다.
1. products를 필터를 돌린다
2. products의 개별의 상품 product에 대해서 .categories.some()으로 한개라도 조건을 만족하는지 판단.
3. product의 categories의 개별의 category에 대해 <br>
   `category.id === targetCategory.id`와 `product.prices.some()`으로 개별의 price가 minPrice와 maxPrice 사이에 있는지

뭐가 문제일까?
<br><br>
너무 다양한 조건과 익명함수, 중첩된 로직이다.

이 하나의 코드에만 맥락이 5개 + a 가 존재한다.

```jsx
const matchedProducts = products.filter((product) => {
  return product.categories.some((category) => {
    const isSameCategory = category.id === targetCategory.id;
    const isPriceInRange = product.prices.some(
      (price) => price >= minPrice && price <= maxPrice
    );

    return isSameCategory && isPriceInRange;
  });
});
```

이렇게 단순하게 명시적으로 어떤걸 비교하는지 확실하게 나열한다면 훨씬 가독성이 좋아지는걸 볼수있다.

### 2. 매직넘버에 이름 붙이기

> **<font color="#c0504d">요약!</font>**<br>
> 하드코딩 please, por favor, NO!

- 직접 데이터에 대한 값을 넣으면 수정과 더불어 의미를 알아차리기 힘들어진다.

#### 애니메이션 delay 예시
```jsx
async function onLikeClick() {
  await postLike(url);
  await delay(300);
  await refetchPostLike();
}
```

뭐가 문제일까?

저기 300이라고 코딩된 숫자가 정확히 무엇을 의미하는지 알아차리기 힘들다.

300ms만큼 애니메이션 시간을 기다리기? 테스트코드? 300ms만큼 서버응답 기다리기?

```jsx
const ANIMATION_DELAY_MS = 300;

async function onLikeClick() {
  await postLike(url);
  await delay(ANIMATION_DELAY_MS);
  await refetchPostLike();
}
```

간단하게 변수로 선언을 해줌으로서 뭘 의미하는지 파악 하기 용이하다.

## 위에서 아래로 읽히게 하기
### 1. 시점 이동 줄이기

> **<font color="#c0504d">요약!</font>**<br>
> 복잡하지 않은 구현은 추상화를 잠깐 양보하도록 해보자!

- 코드의 기능에 비해 과도한 추상화를 하게되면, 가독성이 떨어진다..

#### 사용자 권한에 따른 컴포넌트 변화 예시

```jsx
function Page() {
  const user = useUser();
  const policy = getPolicyByRole(user.role);

  return (
    <div>
      <Button disabled={!policy.canInvite}>Invite</Button>
      <Button disabled={!policy.canView}>View</Button>
    </div>
  );
}

function getPolicyByRole(role) {
  const policy = POLICY_SET[role];

  return {
    canInvite: policy.includes("invite"),
    canView: policy.includes("view")
  };
}

const POLICY_SET = {
  admin: ["invite", "view"],
  viewer: ["view"]
};
```

동작원리는 다음과 같다.
1. useUser훅으로 user를 가져온다.
2. getPolicyByRole메서드로 user.role을 이용해 policy를 가져온다.
	1. POLICY_SET에서 admin, viewer에 따라 사용정책을 bool타입으로 만든다.
3. 가져온 policy로 Button컴포넌트에 disabled속성을 이용해 초대, view의 활성화를 나눈다.

뭐가 문제일까?

현재 정책에 따라 버튼의 활성화상태를 분기하고 있다.

왜 활성화가 되지 않았는지를 확인하기 위해선, <br>
`policy` -> `getPolicyByUser` -> `POLICY_SET`순서로 확인을 해야한다.

이 정도 수준의 간단한 코드에서는 

POLICY_SET과 같은 추상화는 과도한 추상화가 되어, 가독성이 떨어지게 된다.

##### 해결법 A. 조건 펼치기
```jsx
function Page() {
  const user = useUser();

  switch (user.role) {
    case "admin":
      return (
        <div>
          <Button disabled={false}>Invite</Button>
          <Button disabled={false}>View</Button>
        </div>
      );
    case "viewer":
      return (
        <div>
          <Button disabled={true}>Invite</Button>
          <Button disabled={false}>View</Button>
        </div>
      );
    default:
      return null;
  }
}
```

switch-case문을 이용해서 조건분기를 해준 코드이다.

##### 해결법 B. 조건을 한눈에 들어오도록 하기

```jsx
function Page() {
  const user = useUser();
  const policy = {
    admin: { canInvite: true, canView: true },
    viewer: { canInvite: false, canView: true }
  }[user.role];

  return (
    <div>
      <Button disabled={!policy.canInvite}>Invite</Button>
      <Button disabled={!policy.canView}>View</Button>
    </div>
  );
}
```

문제점이었던 과도한 추상화로인해 계속 이리저리 움직이며 확인해야했던것을 해결한 코드이다.
policy에 기본적으로 admin, viewer가 정의되어있고, 
user.role을 키값으로 가지는 policy가 동적으로 할당되게 하였다.

### 2. 삼항 연산자 단순하게 하기

> **<font color="#c0504d">요약!</font>**<br>
> 조건을 복잡하게 쓸바엔 SWITCH나 IF로 해결!

- 삼항 연산자가 중첩될수록 우리의 눈은 더욱 나빠진다.


#### 다중 삼항 연산자 예시

```jsx
const status =
  (A조건 && B조건) ? "BOTH" : (A조건 || B조건) ? (A조건 ? "A" : "B") : "NONE";
```

코드를 설명하지 않아도 될정도로 간단하다.

문제는 딱 보인다.

조건의 조건의 조건의 조건.... 과 같은 형식이라 가독성이 매우 떨어진다.

그럼 어떻게 바꾸면 좋을까?

- if문
```jsx
const status = (() => {
  if (A조건 && B조건) return "BOTH";
  if (A조건) return "A";
  if (B조건) return "B";
  return "NONE";
})();
```

이렇게 else if문 말고 if문 내부에 return문을 작성하여 가독성을 올리는걸 clean code라는 책에서 알려주고 있다.

[난잡한 if-else문 리팩토링](https://inpa.tistory.com/entry/%E2%9A%99%EF%B8%8F-if-else-refactoring#early_return_%EA%B8%B0%EB%B2%95)

- switch문
```jsx
const status = (() => {
  switch (true) {
    case A조건 && B조건:
      return "BOTH";
    case A조건:
      return "A";
    case B조건:
      return "B";
    default:
      return "NONE";
  }
})();
```
